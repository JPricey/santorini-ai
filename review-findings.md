## 1. BUG: history maluses land on the wrong table slots

`search.rs:1305-1316` — after each searched move, a negative adjustment
(malus) is applied:

```rust
search_state.history[current_player_idx].update_move(
    move_idx,          // <-- BUG: this is the loop counter (1, 2, 3, ...)
    ply, move_score_adjustment, prev_move_idx, follow_move_idx,
);
```

Every other call site passes `history_move_hash` (computed at
`search.rs:1146` and used correctly at `:1293` for the beta-cutoff bonus and
`:1332-1339` for the best-move bonus). Here it passes `move_idx`, so all
maluses accumulate in table slots `1..~336` — slots that real move hashes
almost never map to. **Net effect: the history heuristic receives only
positive signals; the "this move was tried and failed" signal is lost
entirely, and slots 1–336 are polluted garbage for any real move that hashes
there.**

Fix is a one-word change. Worth a `compare_engines` run on its own — history
maluses are typically worth real Elo, and this also matters more for
high-branching gods where ordering quality is everything (your lead #1).

**STATUS: FIXED** (`move_idx` → `history_move_hash`). Git archaeology
(2026-07-12): the bug and every history constant (`/60` malus scale, `-4·nd`
clamp, `+75·nd` cutoff bonus, `+3·nd` best bonus, `low_score_cutoff`)
all shipped together in 43a33c2 ("replace move orders with history tables",
Aug 2025) and were **never re-tuned afterward** — later "tune"/"history table"
commits didn't touch them. So no constants were explicitly compensating.
However, the fix has knock-on effects to be aware of:

1. **`low_score_cutoff` pruning goes live for the first time**
   (`search.rs:1116`, used at `:1194`). With the bug, real moves' history
   values could only be non-negative (only bonuses ever reached real hash
   slots; the gravity update keeps values in `[0, MAX]` under positive-only
   bonuses), so `move_score < -750·(depth+1)` was dead code. Post-fix, sums
   can reach −21504 and the break can trigger. It looks sane (drops the
   worst-ordered tail of non-improvers when not in check) but has never been
   validated — if the fix A/B is ambiguous or negative, re-run with that
   break disabled to separate "better ordering" (should be good) from
   "newly-activated pruning" (unvalidated).
2. **Bonus/malus asymmetry is now visible**: +75·nd for the cutoff move vs
   at most −4·nd per fail for others. Chess engines usually run maluses at
   roughly bonus-comparable magnitude. Candidate re-tune after the A/B, not
   a blocker.
3. **Moves that were "best so far" escape maluses** — their inline delta is 0
   at the time they're searched, and there's no retroactive malus pass at
   cutoff (the standard scheme penalizes *all* previously searched moves when
   a later move cuts). Follow-up experiment.
4. The bug was also spraying maluses into pseudo-random slots of the
   response/follow tables (the loop counter got hashed with `prev_move_idx`),
   i.e. low-level negative noise on real entries. The fix removes that too.
5. `Histories::set_move_min` (`search.rs:249`) has **zero call sites** — dead
   code from the same experiments; safe to delete.

**SECOND BUG FOUND (2026-07-12, follow-up audit): response/follow history
read/write slot mismatch.** `HALF_USIZE = size_of::<usize>() / 2` = **4**
(half the *byte* width; the intent was clearly half the *bit* width, 32 —
which the write path hardcoded). So `get_move_score` read at
`hash(move.rotate_left(4) ^ prev)` while `update_move` wrote at
`hash(move.rotate_left(32) ^ prev)` — with an avalanche hash these are
unrelated slots. Consequences: the response and follow tables (the two
*largest-capped* tables, ±8192 vs ±1024/±4096) never returned trained values;
reads returned other pairs' values — noise that dominated the history sum.
Move ordering "by history" was substantially random, which also explains why
the malus fix alone (v123) measured ~neutral. **FIXED**: single
`HISTORY_HASH_ROTATION = usize::BITS / 2` constant used on both paths (also
correct on wasm32, where the old literal 32 was itself broken —
`rotate_left(32)` on 32-bit usize is a no-op rotation).

Fixed-depth node counts across the three snapshots:

| God | Bugged main (v122) | Malus fix (v123) | +Rotation fix (v124) |
|---|---|---|---|
| mortal | 13,809,247 | 12,752,955 | **12,581,212** (−8.9% vs main) |
| hermes | 3,691,292 | 3,146,038 | **3,475,838** (−5.8%) |
| prometheus | 3,400,069 | 3,932,591 | **3,269,677** (−3.8%) |

With both fixes all three suites beat original main; prometheus's v123
regression reversed into the largest gain — consistent with "malus fix was
steering partly on table noise until the rotation fix removed it."

**Remaining history-effectiveness gaps found in the same audit (not bugs):**
- **Histories reset every search** (`SearchState::default()` per
  `negamax_search`) — nothing carries across moves within a game. Chess
  engines persist + decay history game-long (like the TT already does here).
- **Best-move bonus (+3·nd) is applied at every node type**, including
  fail-low (UpperBound) nodes where "best" is weakly informed — standard
  practice is bonus on beta cutoff (and optionally exact/PV nodes) only.
- **Killer only saved when the cutoff move came from the non-improver stage**
  (`search.rs` beta-cutoff branch) — cutoffs found among improvers never
  seed the killer slot.
- Bonus/malus magnitude asymmetry (+75·nd vs at most −4·nd) — see item 2 in
  the malus-fix knock-on list above.

**Measured (visit_tester, fixed-depth node counts, deterministic).** Working
tree (malus fix + Joe's `improving` branch-order fix) vs clean main:

| God (settings) | Bugged main | Fixed | Δ nodes |
|---|---|---|---|
| mortal (`-r 4 -m 4`) | 13,809,247 | 12,752,955 | **−7.6%** |
| hermes (`-r 20 -m 4`) | 3,691,292 | 3,146,038 | **−14.8%** |
| prometheus (`-r 10 -m 4`) | 3,400,069 | 3,932,591 | **+15.7%** |

Follow-up experiment: re-ran the fixed build with `low_score_cutoff` disabled —
hermes and prometheus node counts were **byte-identical**, mortal within 0.3%.
Conclusions:
- The prometheus regression is **not** caused by the newly-live pruning; it's
  ordinary tree-shape chaos from changed ordering (and possibly the combined
  `improving` change). Net across the suite the fix is positive.
- `low_score_cutoff` **still almost never fires** even with working maluses —
  the −4·nd malus is too small to ever push sums near −750·(depth+1). So that
  pruning remains ~dead code. Future tune: larger maluses (chess engines use
  bonus-comparable magnitudes) would both improve ordering signal and make
  this pruning real.
- Definitive adjudication should be a battler `compare_engines` A/B (build old
  vs new `uci` into `all_versions/` per the usual workflow); fixed-depth node
  counts don't capture strength directly.
- Note: the `improving` fix changes semantics (now always compares eval to 4
  plies ago when available, else 2). Chess convention is ply−2 primary with
  ply−4 as fallback for invalid entries; worth an isolated A/B eventually.
  89/89 unit tests pass on the combined tree.

**Related minor bug, same function** — `search.rs:1037-1045`:

```rust
let (improving, eval_delta) = if ply >= 2 { ... }
else if ply >= 4 { ... }   // unreachable: ply>=4 implies ply>=2
```

The `ply >= 4` fallback (presumably intended for when `ss[ply-2]` is invalid,
e.g. after a null move or in-check node) can never execute.

## 2. Training throws away the search scores datagen already produces

The pipeline:
- `datagen/src/main.rs:124-134` writes `score` (search eval) for every position.
- `bullet_prep/src/main.rs:160` explicitly ignores it: `let _score_str = parts[2];`
- The bullet record's `score()` returns `0` and `result()` is outcome-only
  (`santorini-trainer/examples/extra/santorini.rs`), trained with
  `wdl_proportion = 1.0`.

So the net trains on pure win/loss labels. In chess NNUE practice, blending
`sigmoid(search_score)` with the game outcome (lambda around 0.3–0.7 outcome)
is one of the largest single training improvements — outcome-only labels are
extremely noisy per-position (one label shared by ~40+ positions of a game,
including positions where the eventual loser was winning). You are sitting on
the exact data needed to fix this: it's already in every raw file.

Implementation: plumb `score` through `BulletSantoriniBoard` (there's spare
space — the struct is 32 bytes with unused bits in the u128 top; or grow it),
implement `score()`, set `wdl_proportion < 1.0`. Then retrain and A/B.

Also worth revisiting while in there:
- **Position filtering**: positions where the side to move is in check (forced
  response) or where `|score|` is near-winning carry little eval signal;
  standard practice filters or downweights them. Currently every non-terminal
  position is recorded.
- **Datagen search budget** (`datagen/src/main.rs:28-34`): 100k nodes hard cap
  or depth 8 + 20k nodes. Fine, but once score labels matter, label quality =
  search quality; consider raising the depth floor for label purposes.

## 3. Aspiration windows: documented, not implemented

`negamax_search` (`search.rs:428-443`) runs every iterative-deepening
iteration with the full window `(-INFINITY, INFINITY)` — `_root_search`
hardcodes it (`search.rs:499-533`). No aspiration code exists anywhere
(grep confirms). CLAUDE.md's claim that iterations use aspiration windows with
fail-high/fail-low fallback is stale.

Aspiration windows (start with ±~50cp around the previous iteration's score,
widen exponentially on fail) are a standard, low-risk gain — more cutoffs from
tighter bounds at every node. The iterative-deepening skeleton is already
right there. Recommend implementing together with #4 (TT), since fail-high/low
re-searches lean on TT quality.

## 4. Transposition table: always-replace, single slot, no aging

`transposition_table.rs:139-168` — `insert()` unconditionally overwrites
whatever occupies the slot. Consequences:

- A depth-12 PV entry gets stomped by any depth-0 `_q_extend` store that
  happens to collide (`search.rs` stores from qsearch at `q_depth < 2`).
- No generation/age tracking, so within a long search, valuable deep entries
  from the current iteration can't be distinguished from stale ones.
- `TABLE_SIZE` is a hardcoded prime (5M entries × 24 bytes ≈ 120 MB), not
  configurable per use case (datagen threads each allocate one!
  `datagen/src/main.rs:78` — 16 threads × 120 MB = ~2 GB of TTs).

Standard fix: 16-byte packed entries (hash-verification u16/u32 + move u32 +
score i16 + eval i16 + depth u8 + type+age u8 fits), 2–4 entries per bucket,
replacement preferring (same-hash) then (oldest age) then (lowest depth).
This is also the **prerequisite for Lazy SMP** (#8) — you'll want atomic
16-byte or two-u64 entries for lockless sharing.

Bonus: `fetch()` + `insert()` each call `hash_board` — the hash is already on
`state.board.hash`; fine, but the double `get_key` modulo per node could use
the multiply-shift trick that's already commented out at
`transposition_table.rs:131-137`.

## 5. NNUE inference: two cheap speedups, no retraining needed

The diff-based accumulator (`nnue.rs:283-382`) is a nice design, but two
things cost real time:

**(a) Accumulator updates happen even when the eval isn't needed.**
`search.rs:1023-1028`:

```rust
nnue_acc.replace_from_state(&state);        // full diff work, always
let eval = if let Some(tt_value) = &tt_entry { tt_value.eval }
           else { nnue_acc.evaluate() };    // ...but TT eval often used
```

When the TT provides `eval`, the `replace_from_state` work is wasted *at that
node* — its only value is keeping the diff small for a later node. Making the
update lazy (store the target `FeatureSet`; only reconcile the accumulator
when `evaluate()` is actually called) means TT-eval-hit chains do zero SIMD
feature work. The diff logic already handles arbitrary distance between
states, so laziness is safe by construction.

**(b) STM-relative features churn on every ply alternation.** Features are
built from the current player's perspective (`nnue.rs:492-569`): all worker
features move between `ACTIVE_PLAYER_OFFSET` and `OPPO_PLAYER_OFFSET`, and the
matchup-bit feature flips, on every single ply. So evaluating parent→child
costs ~8-12 add/sub rows of 1024×i16 even when the move only changed 2 things.

Fix without touching the trained net: **keep two `LabeledAccumulator`s, one
per side-to-move parity.** When evaluating a node with P1 to move, diff
against the last P1-to-move position (2 plies away, typically 2–4 real feature
changes) instead of the last evaluated position (1 ply away, everything
swapped). Roughly halves feature-update traffic; combines multiplicatively
with (a).

Measure both with `tree_perf` / flamegraph — the harness is already there.

## 6. NNUE architecture: per-god input buckets (the big experiment)

This addresses "specific gods play badly" head-on, and I think it's the most
promising architecture direction given no prior art.

**Today, worker-position weights are shared across all gods.** The feature
"own worker at C3 on height 2" (`nnue.rs:510-521`) has *one* weight row, used
identically whether that worker belongs to Pan (wants to jump down), Hermes
(mobility), or Hades (opponent can't descend...). The *only* god-conditioning
in the whole input is: one matchup bit (1 of 2809, `nnue.rs:488-490`) and
sparse god_data features. A single scalar feature has to bend the entire
1024-wide hidden layer to god-specific geometry — that's a tiny amount of
capacity for what is effectively 50+ different games.

The chess analog is **king-bucketed inputs** (weights conditioned on king
position) — the single biggest NNUE architecture improvement historically.
Here the natural bucket is **own god identity**:

- Worker features become `god_id × (25 squares × 4 heights)` per side —
  ~53 × 100 × 2 = ~10,600 features instead of 200. Sparse-input cost is
  unchanged (same number of *active* features); model size grows from ~7 MB
  to ~28 MB, fine for native.

  **On model size ("won't this explode?"):** it's a ~4× parameter growth,
  not a compute growth. Inference reads only the *active* rows (~12–14 per
  position, same as today), so eval speed is unaffected; the cost is purely
  RAM/disk. For calibration: the existing matchup-bit table is already 2,809
  rows (~5.8 MB — 85% of the current model) for a feature where one row is
  active; per-god worker buckets are ~3.7× that for far richer signal. The
  real risk is **data sparsity** (rare gods train their bucket on few games)
  — mitigate with factorized training (`shared + per_god_delta`, merged at
  save time; bullet supports this). If raw size matters anywhere it's the
  WASM download (model is `include_bytes!`-ed); options: archetype clusters
  (below) at ~13 MB, or a separate smaller web net since native is the
  product.
- Height-map features (the 125 "neutral" ones) can stay shared — that matches
  your intuition about neutral state, and keeps the bucket growth contained.
- If 53 buckets spreads data too thin for rare gods, cluster: bucket gods by
  archetype (mobility gods / build gods / restriction gods / mortal-like) —
  8–12 buckets — or use factorized training (bullet supports feature
  factorization: train per-god weights as `shared + god_delta`).
- The trainer already has the scaffolding: `3_input_buckets.rs` in the
  progression examples, and the data format already carries god ids.

**Secondary, cheaper arch experiments, in order:**
1. **Output buckets by game phase** (#7 in summary — untried per Q11). Bucket
   on total-height-built or max worker height (e.g. 4–8 buckets). Trivial in
   bullet (`2_output_buckets.rs`), tiny inference cost (pick a different
   output row).
2. **Output buckets by matchup/god** — same mechanism, god-conditioned output
   layer instead of input. Cheaper than input buckets, less capacity; a decent
   first test of "does god-conditioning help" before committing to input
   buckets.
3. **Multi-layer** (`4_multi_layer.rs`): 1024→(16→32→1)-style stacks are
   standard now in chess engines and usually beat single-layer at equal nps
   cost with pairwise-multiply tricks. More inference work — needs the #5
   speedups landed first to afford it.
4. Revisit dual-perspective *only if* per-god buckets land — your original
   objection (neutral heights dominate) stays valid; I wouldn't reopen it.

One inconsistency to clean up while touching this: `NNUE_GOD_COUNT = 53` in
`nnue.rs:57` vs `NUM_GODS = 39`/`29` in `bullet_prep/src/main.rs:36` and the
two trainer example variants — the dead `map_features` copies in bullet_prep
and the older trainer block are drift hazards. Single-source these constants
(a tiny shared crate or codegen'd include) so the engine/prep/trainer triple
can't silently disagree.

## 7. High-branching gods (your lead #1): measure, then stage

Confirmed the shape of the problem: `MAX_MOVE_COUNT = 336`
(`move_picker.rs:15`), and Poseidon's generator (`poseidon.rs:611-753`)
enumerates every build multiset eagerly — every node allocates and fills the
full list even if the first move causes a beta cutoff. The `MovePicker` is
staged *for scoring* (non-improvers scored lazily, `move_picker.rs:198-207`)
but not for *generation*.

However — before building staged generation (which is invasive given the
function-pointer god architecture), note the ordering:

1. **Fix #1 (malus bug) first** — ordering quality directly reduces how many
   of those 336 moves get searched.
2. **Measure**: add a per-god variant of `tree_perf` (it currently hardcodes
   Mortal, `tree_perf.rs:16-18`) and get nodes/sec + effective branching
   factor per god. You can't tune what you don't measure, and it'll rank
   Poseidon vs Morpheus vs Hermes vs Artemis properly.
3. **Cheap structural win**: allocation reuse. Every node calls
   `get_sized_result` → fresh `Vec::with_capacity(128)`
   (`move_helpers.rs:78-81`) plus `MovePicker` construction. A per-ply
   preallocated buffer pool in `SearchState` (127 plies × 336 × 8 bytes ≈
   340 KB total) eliminates all movegen malloc traffic.
4. **Then staged generation** if still needed: generate move+first-build
   pairs eagerly, expand extra-build continuations only when the picker
   actually reaches that move. Natural fit: a per-god "expand" function
   pointer alongside the existing generator; only implement it for the ~4
   explosive gods, default = current behavior.

Also note `search.rs:1201-1209` already soft-breaks on late non-improvers at
frontier nodes, and `low_score_cutoff` prunes by history score — both get
strictly better once history signals are fixed (#1) and decomposed (#8).

## 8. Feature-decomposed history (your lead #2): yes, and here's the shape

Confirmed your diagnosis: `get_history_idx` packs the *entire* move identity —
e.g. Poseidon (`poseidon.rs:168-185`) folds from+height, to+height, and up to
four builds+heights into one index via `HistoryIdxHelper` (`gods.rs:1191-1241`).
A 4-build Poseidon move's index is nearly unique → the four history tables
(global/ply/response/follow, `search.rs:170-294`) almost never see repeats for
big-god moves → history ≈ noise exactly where ordering matters most. (Mortal
and other 3-field gods are fine — 100³ combinations repeat plenty.)

Proposed design, compatible with the existing architecture:

- Replace `get_history_idx(board) -> usize` with
  `get_history_features(board, &mut ArrayVec<u32, 8>)` emitting 2–4 *generic*
  features per move:
  - `MOVE(from_sq, from_h → to_sq, to_h)` — one feature, shared vocabulary
    across all gods (~10k ids)
  - `BUILD(sq, new_height)` — one feature *per build* (~125 ids), so a
    Poseidon quad-build contributes 4 independently-learned build features
  - optional god-specific extras (swap/push target, wind direction…)
- Score = sum of table values over the move's features (like the existing
  4-table sum, just per-feature); update = apply bonus/malus to each feature.
- Keep one combined-index table too if you want — "exact move" history and
  "feature" history are complementary (chess engines stack butterfly +
  continuation + capture histories the same way).

Cost: a few more table lookups per scored move; the picker already defers
scoring of non-improvers, so the hot path impact is bounded. This directly
attacks both "move picking is inaccurate for big gods" and — via
`low_score_cutoff` pruning — search tree size.

Half-measure if you want a 1-day test: keep the current tables but *also* add
just the `BUILD(sq,height)` feature table and sum it in. If it moves Elo for
Poseidon/Morpheus matchups, the full decomposition is justified.

## 9. Lazy SMP (multithreading) — the big native-strength lever

Search is single-threaded (`engine.rs` = one worker thread; `search.rs` has no
parallelism). At native tournament conditions, 1→4 threads of Lazy SMP is
typically worth more than any single algorithmic change on this list.

Route: shared TT with atomic entries (needs #4's 16-byte repack), N threads
searching the same root with staggered depths/jitter, shared stop flag
(`StopFlagSearchTerminator` already exists), thread 0 owns reporting.
Histories/killers stay thread-local. `EngineThreadWrapper` grows a thread
count; battler/uci get a `--threads` flag (battler comparisons must then pin
equal threads per side).

You flagged the desktop UI consequence yourself — moving `ui` to talk UCI
instead of embedding is the cleaner long-term shape anyway and decouples GUI
frame time from search CPU.

Sequencing: do #4 first regardless; do SMP when you want a step-change and
have an evening to chase race conditions.

## 10. Grab-bag (each small, roughly descending value)

- **Second killer slot** — `killer_move_table` holds one killer
  (`search.rs:300`); CLAUDE.md says two. Two-killer is standard and cheap.
- **Correction history** — modern engines keep a table of "static eval error
  by structure key" (here: hash of height map, or height map + workers) and
  correct `eval` before pruning decisions. Directly targets your "eval
  accuracy" complaint without retraining, and it's ~50 lines.
- **Singular extensions / multicut** — you have TT depth+bound info already;
  standard gains at higher depths.
- **`get_history_hash` computed twice per move** — once in the picker for
  scoring (`move_picker.rs:137-141`), once in the search loop
  (`search.rs:1146`). Cache it in `ScoredMove` (there's room — it's
  `{u32, i16}`; widening to carry a u32 hash keeps it ≤ 16 bytes).
- **`_q_extend` stand-pat asymmetry** — when not in check it returns
  `eval.min(beta)` immediately (`search.rs:768-772`); the side to move never
  gets to try its own checks. Given "no tactical blunder" feel, low priority,
  but if you ever see horizon weirdness in won positions, look here first.
- **Datagen TT memory** — 120 MB TT per datagen thread (see #4); a small CLI
  size knob frees RAM for more threads.
- **Testing rigor** — if not already: fixed opening books per matchup +
  SPRT-style stopping in `compare_engines` makes every experiment above
  cheaper to adjudicate. All the findings here should be gated on battler
  results, not vibes. See "A/B testing system recommendations" below.
- **Docs drift** — CLAUDE.md: aspiration windows (don't exist), 2 killers

# A/B testing system recommendations (added 2026-07-12)

Context: `compare_engines` plays one deterministic color-swapped pair per
matchup (~1300 matchups), 0.5s/move, half the cores. Re-running gives
identical results, and multiplying games per matchup is expensive. Changes
already made: mirror matchups now run first, and mortal v mortal is always
included.

Key reframe: **matchup diversity IS the opening book.** 1300 matchups × 1
pair extracts more independent signal than 300 matchups × 4 identical pairs
would. The single-pair design isn't the weakness. The weaknesses are, in
order of fix ROI:

1. **No aggregate statistic.** The `!!!` sweep lines are eyeballed. Add
   pentanomial pair scoring (WW / WL+LW / LL counts) with a significance
   summary — normal-approx z on (sweeps_for − sweeps_against), or an Elo ±
   CI. Pure post-processing of `tmp/engine_cmp.csv` (could live in
   `read_matchups.py` or print live in compare_engines). Zero extra compute;
   converts every run already made into a defensible verdict.
2. **Fixed-node game mode.** Wall-clock moves are load-sensitive and force
   workers = cores/2. A `-n <nodes>`-per-move mode
   (`StaticNodesVisitedSearchTerminator` already exists; UCI needs to accept
   it) gives perfectly reproducible games, all cores usable, and isolates
   search-*shape* changes from speed. Measure speed separately
   (visit_tester/tree_perf). Use time-based runs only when the change is a
   speedup.
3. **Early stopping.** With mirrors (most informative games) now first,
   maintain a running sequential test over pair outcomes and stop when the
   bound is crossed. Most A/Bs resolve well before 1300 pairs — this is the
   main cost saver. (Caveat: fixed finite population, so treat bounds as
   heuristic, not exact SPRT.)
4. **Targeted resampling instead of global multiplication.** When a result
   is borderline, don't rerun (no new info) and don't multiply everything —
   expand only ambiguous/interesting matchups with K extra pairs from seeded
   random openings: `get_random_state_flattening_powers` with fixed seeds
   (already exists; datagen uses it), filtered for near-equal quick-search
   eval like a chess book. Deterministic, reproducible, and cost lands only
   where the signal is thin.
5. **Per-matchup regression diffing.** Keep each run's CSV; diff sweep
   outcomes between versions to catch god-specific regressions even when the
   aggregate is flat — directly serves the "specific gods play badly" goal.
6. **Anchor ladder.** Occasionally run new versions against older anchors
   (e.g. v113, v120), not just the immediate predecessor — small consecutive
   diffs can accumulate drift that A-vs-B never sees.
7. Nit: worker logs (`compare-*.log`) scatter into the CWD; route to
   `tmp/logs/`.
